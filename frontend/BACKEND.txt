========================================
WHATSAPP (ARQUITECTURA)
========================================
El corazon del producto es que el cliente se entere del estado.

HOY (modo link):
- Al cambiar status, el backend CREA una fila en notifications
- El frontend abre wa.me con ese mensaje (el mecanico aprieta enviar)

DESPUES (modo api):
- Misma tabla notifications
- El backend envia solo por WhatsApp Business API (Meta)
- Switch por taller: whatsappMode = "link" | "api"

Asi no se rehace el frontend de Martin.

Tabla notifications:
- id, workshopId, orderId, clientId
- channel (whatsapp), toPhone, message
- status: pending | link_ready | sent | failed
- triggeredByUserId, createdAt, sentAt?

========================================
ENDPOINTS
========================================

CLIENTES
- GET /clients
- POST /clients  { name, phone, notes? }
- GET /clients/:id
- PATCH /clients/:id

VEHICULOS
- GET /vehicles?clientId=
- POST /vehicles  { clientId, plate, brand?, model? }
- GET /vehicles/:id
- PATCH /vehicles/:id
- GET /vehicles/:id/history

ORDENES
- GET /orders?open=true&page=1&limit=20
  Cada orden INCLUYE:
  client: { id, name, phone }
  vehicle: { id, plate, brand, model }
  vehicleOrItem: "string armado"
  photos: [{ id, url, createdAt }]

- POST /orders
  { clientId, vehicleId, title, description, estimatedAt?, status? }
  (alternativa: enviar plate/brand/model y el backend crea/asocia vehiculo)

- GET /orders/:id

- PATCH /orders/:id
  SOLO editar campos (title, description, etc.)
  NO cambia status. NO dispara aviso.

- POST /orders/:id/status
  body: { "status": "listo" }
  → cambia estado + historial + crea notification
  → si whatsappMode=api, envia automatico

FOTOS (varias, no una)
- Storage: Cloudflare R2 (no disco del servidor)
- POST /orders/:id/photos  (multipart)
- Ya no usar photoUrl singular

EQUIPO DEL TALLER (solo el dueno)
- GET /users                lista el equipo, incluidos los apagados
- POST /users               crea un mecanico { name, email, password }
                            el rol lo pone el backend: siempre mechanic
- PATCH /users/:id          { name?, active? }
- POST /users/:id/password  { password }  le cierra la sesion abierta

PANEL DE SOLVE (solo platform_admin)
- PATCH /admin/workshops/:id           { name?, phone?, active? }
                                       active:false suspende el taller
- DELETE /admin/workshops/:id          da de baja (204). No borra datos
- POST /admin/workshops/:id/restore    revive un taller dado de baja
- GET /admin/workshops?archived=true   solo los dados de baja
- GET /admin/workshops/:id/users       el equipo de un taller
- POST /admin/workshops/:id/users      alta de respaldo
                                       { name, email, password, role? }
- POST /admin/accounts                 otra cuenta de Solve (clave de 12+)
- GET /admin/accounts                  las cuentas de Solve
- PATCH /admin/accounts/:id            { name?, active? }

Notas:
- Apagar a alguien no lo borra: sigue en GET /users con active:false.
- Suspender un taller deja fuera a su gente en el siguiente request, no al
  vencer el token.
- Un dueno que pida por alguien de otro taller recibe 404, no 403.
